# GSC 레시피 색인 전수 조사 수직 슬라이스

설계: `docs/superpowers/specs/2026-08-14-gsc-recipe-index-audit-design.md`

## 글로서리

| 용어 | 코드 용어 | 뜻 |
| --- | --- | --- |
| 조사 | `audit` | 고정된 레시피 URL 집합을 한 번씩 검사해 색인 상태 분포를 완성하는 작업 |
| 조사 대상 | `inventory` | sitemap 0~3에서 중복을 제거하고 최초 초기화 때 고정한 URL 목록 |
| 시도 | `attempt` | URL Inspection API 호출 한 번. 요청 직전에 기록하며 재시도도 별도 시도 |
| 성공 결과 | `successful result` | HTTP 200으로 받은 URL Inspection 결과 |
| 완료 URL | `completed URL` | 성공 결과가 하나 이상 저장된 조사 대상 URL |
| 미완료 URL | `pending URL` | 성공 결과가 아직 없는 조사 대상 URL |
| 재개 | `resume` | 완료 URL은 건너뛰고 첫 미완료 URL부터 조사를 이어가는 동작 |
| 호출 여유 | `allowance` | 최근 24시간 최대 1,800회 중 아직 사용할 수 있는 시도 수 |
| 상태 집계 | `status breakdown` | 완료 URL을 `색인됨`과 GSC `coverageState` 원문별 개수로 나눈 결과 |
| 요약 | `summary` | 조사 진행률, 상태 집계, 오류와 다음 실행 가능 시각을 담은 파생 결과 |

## 범위 밖

다음 항목은 의도적으로 구현하거나 테스트하지 않는다.

- 레시피 sitemap 4번 이상 — 테스트 없음
- 일반 페이지·재료·다국어 sitemap — 테스트 없음
- GSC Search Analytics 결합 — 테스트 없음
- 실시간 URL 검사와 색인 요청 — 테스트 없음
- cron·GitHub Actions 등 자동 실행 — 테스트 없음
- 웹 대시보드 — 테스트 없음
- 완료 URL의 정기 재검사와 새 조사 생성 — 테스트 없음
- 다른 프로세스가 소비한 GSC 할당량 추적 — 테스트 없음

## 슬라이스 1 — 첫 URL을 검사하고 상태 집계를 확인한다

이 슬라이스는 전체 경로를 가장 얇게 관통하는 walking skeleton이다. 사용자는 sitemap 0~3으로 조사 대상을 확정하고, 첫 미완료 URL의 성공 결과가 저장된 뒤 상태 집계가 1건 증가하는 것을 확인할 수 있다.

### Acceptance Criteria

- **AC-1.1:** 유효한 sitemap 0~3으로 초기화를 실행하면, 시스템은 URL을 중복 제거한 조사 대상을 저장하고 sitemap별 행 수·중복 행 수·고유 URL 수를 보여준다.
- **AC-1.2:** 같은 URL이 여러 sitemap에 있으면, 시스템은 이를 조사 대상 하나로 저장하면서 해당 URL이 나온 모든 sitemap index를 보존한다.
- **AC-1.3:** 유효한 인증으로 조사를 실행하고 첫 미완료 URL이 HTTP 200 결과를 받으면, 시스템은 시도와 성공 결과를 저장하고 해당 URL을 완료 URL로 표시한다.
- **AC-1.4:** 성공 결과 하나가 저장된 뒤 요약을 생성하면, 시스템은 검사 완료 1건과 해당 결과의 `색인됨` 또는 `coverageState` 상태 집계 1건을 보여주며 두 개수의 합이 일치한다.
- **AC-1.5:** 외부 호출 없이 요약을 다시 요청하면, 시스템은 저장된 조사 대상과 이벤트만 사용해 같은 상태 집계를 재생성한다.
- **AC-1.6:** `--init`, `--run`, `--summary` 중 아무 동작도 지정하지 않거나 여러 동작을 함께 지정하면, 시스템은 사용법을 보여주고 조사 데이터를 변경하거나 외부 호출을 시작하지 않는다.

## 슬라이스 2 — 중단된 조사를 중복 호출 없이 재개한다

사용자는 여러 날에 걸쳐 명령을 반복 실행해도 완료 URL을 다시 검사하지 않고, 강제 종료 시점의 기록을 잃지 않은 채 미완료 URL부터 이어갈 수 있다.

### Acceptance Criteria

- **AC-2.1:** 성공 결과가 있는 완료 URL과 성공 결과가 없는 미완료 URL이 함께 있을 때 재개하면, 시스템은 완료 URL을 건너뛰고 inventory 순서상 첫 미완료 URL부터 검사한다.
- **AC-2.2:** 시도는 기록됐지만 대응하는 성공 결과 없이 실행이 종료되면, 시스템은 그 시도를 최근 24시간 사용량에 포함하면서 해당 URL은 미완료 URL로 유지한다.
- **AC-2.3:** 기존 조사 대상이 있는 상태에서 초기화를 다시 요청하면, 시스템은 기존 조사 대상과 이벤트를 덮어쓰지 않고 종료한다.
- **AC-2.4:** 조사 도중 프로덕션 sitemap 내용이 바뀌더라도 재개하면, 시스템은 최초에 고정한 조사 대상만 사용한다.
- **AC-2.5:** 모든 조사 대상에 성공 결과가 생기면, 시스템은 남은 URL 0개를 보여주며 검사 완료 수와 모든 상태 집계의 합을 전체 고유 URL 수와 동일하게 보여준다.

## 슬라이스 3 — 호출 여유와 요청 간격 안에서 조사한다

사용자는 반복 실행과 재시도가 있어도 스크립트 자체의 최근 24시간 시도 수와 분당 호출 속도가 설정한 안전 범위를 넘지 않는 것을 확인할 수 있다.

### Acceptance Criteria

- **AC-3.1:** 연속된 URL을 검사하면, 시스템은 각 시도 시작 사이에 최소 250ms 간격을 둔다.
- **AC-3.2:** 최근 24시간 시도가 1,800회에 도달한 상태에서 재개하면, 시스템은 새 시도를 시작하지 않고 다음 호출 여유가 생기는 시각을 보여준다.
- **AC-3.3:** 최근 24시간 시도가 1,799회인 상태에서 재개하면, 시스템은 최대 한 번만 새 시도를 시작한 뒤 추가 시도를 멈춘다.
- **AC-3.4:** 네트워크 오류 또는 `5xx`로 재시도하면, 시스템은 각 재시도를 별도 시도로 기록하고 지수 백오프와 jitter를 적용하며 최대 두 번까지만 재시도한다.
- **AC-3.5:** URL Inspection API가 `429`를 반환하면, 시스템은 해당 결과를 기록하고 재시도나 다음 URL 호출 없이 현재 실행을 종료한다.

## 슬라이스 4 — 인증·입력·저장 오류에서 기존 조사를 보존한다

사용자는 인증이나 입력 데이터가 잘못돼도 기존 조사 기록이 손상되지 않으며, 복구할 수 없는 요청 오류와 재시도 가능한 오류가 구분되는 것을 확인할 수 있다.

### Acceptance Criteria

- **AC-4.1:** 인증 또는 property 접근 확인이 `401`이나 `403`으로 실패하면, 시스템은 URL Inspection 시도를 시작하지 않고 기존 조사 대상·이벤트·요약을 유지한 채 권한 오류로 종료한다.
- **AC-4.2:** 특정 URL이 `429` 이외의 `4xx`를 반환하면, 시스템은 이를 재시도하지 않는 요청 오류로 기록하고 해당 URL을 미완료로 둔 채 다음 URL을 검사한다.
- **AC-4.3:** sitemap이 비어 있거나 허용되지 않은 origin·경로의 URL을 포함하면, 시스템은 기존 조사 데이터를 덮어쓰지 않고 GSC 호출 전에 초기화에 실패한다.
- **AC-4.4:** 이벤트 로그에 파싱할 수 없는 행이 있으면, 시스템은 기존 파일을 수정하거나 GSC를 호출하지 않고 오류 행의 위치를 알려준다.
- **AC-4.5:** 초기화·조사·요약을 실행한 뒤 생성 파일과 콘솔 출력을 확인하면, 시스템은 credential·access token·Authorization 헤더를 포함하지 않는다.

## 구현 순서

1. 슬라이스 1로 조사 대상 → 첫 API 결과 → 상태 집계의 전체 경로를 증명한다.
2. 슬라이스 2로 여러 실행에 걸친 재개와 완료 판정을 추가한다.
3. 슬라이스 3으로 rolling 24시간 호출 여유, 요청 간격, 재시도와 429 중단을 고정한다.
4. 슬라이스 4로 인증·입력·저장 오류에서 기존 데이터가 보존되는 것을 완성한다.
